# Technical Guidelines & Engineering Rules

## 1. Non-Negotiable System Constraints

```
+-----------------------------------------------------------------------------------+
|                           NON-NEGOTIABLE CONSTRAINTS                              |
+------------------------------------+----------------------------------------------+
| Bundle Size Cap                    | < 5.0 MB Total (including PWA SW & assets)   |
| Cold-Start Time                    | < 3.0 Seconds to interactive local UI         |
| Main-Thread Execution              | Zero Blocking Remote Network Calls           |
| Offline Capability                 | 100% Offline Functional from Cold Start      |
| Output Schema Contract             | Strict match to schema.json & x-devcraft-voc |
+------------------------------------+----------------------------------------------+
```

---

## 2. Technical & Performance Rules

### 2.1 Bundle Size & Dependency Constraints
- **Bundle Cap:** Total production build (JS, CSS, HTML, Service Worker) must not exceed **5.0 MB**.
- **Package Selection Policy:**
  - Mandatory use of lightweight libraries: React 18, Vite, Dexie.js, Lucide-React (tree-shaken icons).
  - Heavy NLP/ML client libraries (e.g. `@tensorflow/tfjs`, `transformers.js`, `spacy-js`) are **PROHIBITED** to preserve bundle footprint and cold-start performance.
  - Zero heavy utility libraries like `lodash` or `moment.js`; use native JavaScript/TypeScript utilities and standard `Date` math.

### 2.2 Thread Execution & Network Isolation
- **Non-Blocking Main Thread:** Local CRUD operations and UI navigation must NEVER wait on network calls.
- **Async Execution:** Online API calls to Gemini 1.5 Flash MUST be wrapped in strict timeout blocks (max 2500ms). If network is absent or timeout expires, immediately fallback to the local offline NLP parser.
- **Airplane Mode Cold Start:** The application MUST load directly from Cache/Service Worker in airplane mode without displaying network error overlays.

## 3. Code Standards & Schema Governance

### 3.1 Strict TypeScript & Type Safety
- `noImplicitAny: true`, `strictNullChecks: true`, `noUnusedLocals: true`.
- Schema objects MUST match `schema.json` types explicitly:
  ```typescript
  export interface OrderItem {
    description: string;
    quantity: number;
    attributes: Record<string, string | number | boolean>;
  }

  export interface OrderRecord {
    customer: string | null;
    items: OrderItem[];
    due_date: string | null; // ISO-8601 YYYY-MM-DD
    amount: number | null;
    references_prior_order: boolean;
    confidence: number;
    needs_clarification: boolean;
  }
  ```

### 3.2 Closed-Set Domain Attribute Key Rules
- Attribute keys generated by parsers MUST strictly belong to the domain's vocabulary defined in `x-devcraft-vocabulary`:
  - `tailor`: `["color", "fabric", "chest", "waist", "length", "sleeve", "size", "fit"]`
  - `tiffin`: `["portion", "spice_level", "meal", "roti_count", "jain", "days"]`
  - `electrician`: `["appliance", "issue", "room", "brand", "wattage"]`
  - `baker`: `["flavour", "weight_kg", "egg_free", "tier", "message_on_cake", "shape"]`
- **Rule:** Any key outside these domain sets is invalid and scores as wrong in `score.py`. Parsers MUST drop unknown keys before output generation.

### 3.3 Defensive Schema Validation & Error Boundaries
- Every parsed record MUST pass a schema validator function before being written to IndexedDB or returned by the CLI runner.
- Every major UI component must be wrapped in a React Error Boundary to prevent application crashes during unexpected data states.

## 4. Operational Boundaries & AI Governance

### 4.1 Strict Failure Safety ("Do Not Hallucinate")
- **Rule:** If a message field is ambiguous, unreadable, or missing a mandatory domain blocking attribute (`flavour` for baker, `issue` for electrician), **DO NOT GUESS OR HALLUCINATE VALUES**.
- Set `needs_clarification: true` and output `null` for unresolvable dates/fields.
- *Reasoning:* Confident incorrect values score significantly worse in evaluation than flagged uncertainty.

### 4.2 Raw Data Integrity Preservation
- **Rule:** Raw input messages, received timestamps, and original op-log entries MUST NEVER be overwritten or deleted.
- Raw message records in IndexedDB serve as the single source of truth for re-parsing, auditing, and conflict playback.

### 4.3 Inline Architectural Auditability
- All code modules (parsers, date resolvers, sync log mergers) MUST include inline docstrings explaining:
  1. The exact rule or scenario being satisfied.
  2. The theoretical basis (e.g., Lamport clock sorting, token-set F1 normalization).
  3. Failure fallback behavior.
- *Reasoning:* Hackathon judging requires team members to explain any line of code chosen at random by judges.
